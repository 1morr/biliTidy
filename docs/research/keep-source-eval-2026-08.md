# 實測：來源收藏夾要不要給模型一個 id（2026-08-31）

## 為什麼測

`target_folder_ids` 原本的語意是二選一：回空陣列＝留在原地，回目標 id＝**搬走**。來源收藏夾刻意不列 id
（當時的理由：給了 id 只會誘導模型把它當答案）。代價是模型表達不出「這支同時屬於現在這個夾與另一個夾」。

實際跑一次已經分好的收藏夾就看得到這個資訊損失。整理某個「百合」夾時，模型自己在理由欄寫著
「標籤含音声**與百合**」，卻只能把影片判給 `Sound`——也就是從百合夾**搬走**。它沒有分錯，是合約
逼它二選一。

**新合約**：來源夾也給短號（固定 1，目標從 2 開始），`target_folder_ids` 改成「這支最後應該在哪些
收藏夾裡」。三種答案都表達得出來：`[1]` 留在原地、`[1,3]` 留在原地並複製一份到 3、`[3]` 搬走。

要驗的是兩件事，第二件才是真正的風險：

1. **命中率會不會掉**——模型還找不找得到正確的目標收藏夾。
2. **會不會什麼都保留**——來源夾一旦變成可選項，模型可能每次都把它列進去，等於什麼都不搬。

## 方法

- 資料：與 [`classify-eval-2026-08.md`](classify-eval-2026-08.md) 同一份 fixture（真實帳號的預設收藏夾，
  62 支有效影片、36 個收藏夾、真實 `view/detail` 詳情），同一份人工基準答案（36 支沒有爭議的影片）。
- 端點與模型：同一個 OpenAI 相容端點、`deepseek-v4-flash`、關閉思考模式、純文字（不附圖）、每批 30 支。
- 程式碼：走擴充功能真正在用的 `classify()`。舊合約用同一組組裝函式重建（來源夾那一行拿掉 id、
  系統提示的三段字句換回舊版），任何一段替換失敗就直接丟錯，避免「以為在比較舊合約、其實跑的是新的」。
- 兩個情境（同一批影片，只換「目前所在收藏夾」是哪一個）：
  - **S1 雜物夾**：來源＝`默认收藏夹`，描述「還沒分類的雜物夾，什麼都可能有」。62 支都該找到新家。
  - **S2 已分好的夾**：來源＝`Windows`（描述是真正的收錄標準）。基準答案裡 16 支的正確答案就是
    「留在 Windows」，其餘 20 支該搬到各自的夾。這是使用者真正會遇到的情境。
- 每個組合跑 2 次以上（端點本身的浮動見 `classify-eval-2026-08.md`：同一份 prompt 重跑約 20% 的決策會變）。

## 結果

命中率＝基準答案裡「該搬走」那幾支有沒有搬到正確的夾。「仍在來源」＝基準答案是「該留下」的 16 支，
最後是否還在來源夾（回空陣列或「留下並複製」都算留住）。

| 情境 | 合約 | 命中率 | 該留的仍在來源 | 留下並複製 |
| --- | --- | --- | --- | --- |
| S1 雜物夾 | 舊 | 100% / 97% | — | 表達不出來 |
| S1 雜物夾 | 新（**未加**防錨定規則） | 97% / 100% | — | **1 / 29** |
| S1 雜物夾 | 新（加規則後） | 100 / 97 / 100 / 100% | — | 1 / 1 / 1 / 1 |
| S2 已分好的夾 | 舊 | 95% / 100% | 16/16、15/16 | 表達不出來 |
| S2 已分好的夾 | 新（加規則後） | 95 / 100 / 100 / 95% | 16/16 ×4 | 8 / 2 / 0 / 4 |

### 1. 命中率沒有變

四次新合約對兩次舊合約，兩個情境都落在 95–100%，全部在判讀門檻（±5 個百分點）之內。給來源夾一個 id
**沒有**讓模型變得找不到正確的目標。

### 2. 「什麼都保留」確實會發生，觸發條件是來源夾的描述

第一版新合約在 S1 跑出 1 與 29（62 支裡 47%）的兩極結果。看理由就知道原因：

```
【黄金时代Ep.1】十年前的ITX：联力PC-O5S → 留在原地＋Windows | 標籤有硬體、機箱、ITX
适合全NAS系统的低成本云端加密块备份方案       → 留在原地＋Windows | 標籤含NAS、備份
```

來源夾的描述是「還沒分類的雜物夾，**什麼都可能有**」——照字面讀，任何影片都符合它的收錄標準，
所以「留在原地」永遠成立。**舊合約下這句話無害**（描述只是背景資訊），**新合約下它變成一條判準**。

修法是在系統提示補一條：

> 「目前所在收藏夾」的描述空白、含糊，或本身就是「什麼都收」的暫存夾時，不算符合它的收錄標準：
> 這種影片要找一個真正對應的目標收藏夾，不要因為「放這裡也可以」就把它列進去。

加上之後 S1 四次都是 1，兩極消失。

### 3. 真正的目的達到了

S2（已經分好的夾）四次都是 16/16 留住該留的，而且開始出現正確的「兩個都算」：

```
一分钟教你用h3制作动态壁纸  → 留在 Windows ＋ 複製到 Ai   | 標籤含AI與教程
🔥74.2k Star，Immich    → 留在 Windows ＋ 複製到 Ai   | 標籤含開源項目
```

`h3 做動態桌布` 正是 `design.md` 6.1 當初拿來說明「一支影片本來就屬於兩個夾」的例子。舊合約的第 2 次
把 `Immich` 直接**搬去** `Ai`（於是它離開了 Windows）；新合約把它變成「留下並複製」。

## 判讀與限制

- 「留下並複製」的支數在 S2 是 0–8（0–13%），四次之間浮動明顯，比命中率不穩。裡面也有判錯的：
  某次把一支粵語 vlog 判成「留在 Windows ＋ 複製到 Cantonese」（它本來就不該在 Windows）。
  **這是預設值的品質問題，不是資料安全問題**：審核表每一列都寫著「留在來源，另外複製一份出去」，
  一鍵就能改回搬走，而且複製比搬移更不具破壞性。
- S2 是把 62 支預設收藏夾的影片「當作」放在 `Windows` 夾裡送進去（prompt 不驗證這件事），所以裡面
  混著一批本來就不屬於 Windows 的影片。真實的「已經分好的夾」雜訊會比這低。
- 只測了一個端點、一個模型、純文字模式。附圖模式沒有另外測——copy 與 move 的差別在寫入端，不在
  送出去的內容，沒有理由認為附圖會改變這個結論，但也沒有量過。

## 結論

採用新合約。命中率沒有代價，換到的是模型表達得出「兩個都算」——那是舊合約結構上做不到的事。
防錨定那條規則是必要的：少了它，一個寫得含糊的來源夾描述就會讓將近一半的影片留在原地。

# 這個擴充功能是怎麼運作的

給「想知道按下去之後發生什麼事」的人看。想知道**為什麼這樣設計**請看 [design.md](design.md)，
想知道**實測數據**請看 [research/](research/)。

---

## 一句話

它做兩件「先審核、再批次收拾」的事：

- **整理收藏**：讀你的 B 站收藏夾，把每支影片的資訊（標題、標籤、合集…）連同「每個收藏夾收什麼」一起交給你自己的 AI 端點，
  AI 回答「這支該放哪」，**你看過、確認過**之後才真的搬。
- **清理關注**：讀你的關注清單，向 B 站查每個帳號最後一次投稿是什麼時候，攤成一張表；你設門檻、篩選、勾選、確認，
  它再一個一個取關。按錯了，一顆按鈕把人全部關注回來、分組也放回去。

## 五個地方

| 在哪裡 | 做什麼 | 會不會動到你的帳號 |
|---|---|---|
| 「整理」分頁 | 選來源夾 → 選目標夾 → 分類 → 審核 → 搬移或複製 | 只有按下作業列那顆按鈕才會 |
| 「收藏夾」分頁 | 寫、生成、匯入、同步每個夾的**描述**；新增收藏夾 | 「同步回 B 站」與「新增」會 |
| 「關注」分頁 | 準備 → 查 → 審核 → 取關 → 撤銷 | 只有按下作業列那顆「取關 N 個」並二次確認才會 |
| 「設定」分頁 | AI 端點、要餵多少資料給 AI、自訂指示、限速、快取、備份、語言 | 不會 |
| B 站影片頁的 ✨ 智慧收藏 | 對眼前這一支影片問一次 AI，直接收藏 | 會（但 10 秒內可以按「取消收藏」） |

沒有「刪除收藏夾」——那在 B 站是連影片一起消失且不可復原的操作，整理流程用不到它。
也沒有分組管理、拉黑、粉絲操作——那些不是清理關注的工作。

**兩種長任務一次只跑一個。** 整理收藏與清理關注共用同一把讀取節流器與 Web Lock；一個在跑的時候，
另一頁的主按鈕與寫入按鈕變灰，旁邊寫著「另一個任務還在跑——等它跑完，或到那一頁停止它」。
分頁之間切換不會打斷任務，切回來畫面接得上。

## 收藏夾整理最重要的概念：「描述」

描述就是**你告訴 AI「這個夾子收什麼」的那句話**。整套東西的準確度幾乎都押在它身上：
實測把描述從 `游戏视频` 這種標題級文字改寫成一句真正的收錄標準，命中率 94% → 100%
（[實測](research/classify-eval-2026-08.md#2-收藏夾描述是投報率最高的一件事)）；
相比之下「全部附圖」多花 62 次請求與 65% token，反而更差。**先寫描述，再調設定。**

- 描述存在**本機**（`chrome.storage.local`），不會自動寫回 B 站。
- **沒寫描述時會自動改用 B 站那個收藏夾的簡介**（介面上會標「來自 B 站簡介」）。兩個都空，AI 就只剩夾子名稱可看。
- 整理流程與影片頁的「智慧收藏」用的是**同一份**描述，編輯入口只有「收藏夾」分頁一個。

寫描述有三條路，結果都只是**草稿**，按「採用」才存進本機：

| 做法 | 說明 |
|---|---|
| 手寫 | 想寫多長都可以 |
| 從 B 站簡介匯入 | 把夾子在 B 站的簡介抓過來（收藏夾清單那一個請求就帶回來了，不用額外請求） |
| AI 生成 | 在整個收藏夾裡**平均抽最多 6 頁**（≤240 支候選，再抽稀到 80 支）交給模型歸納 |

**AI 生成的是一句 20 字以內的話**（目標 10 字左右），例如「插畫與繪師作品」「粵語翻唱與改編」。
刻意寫短、寫寬：描述越細，下一次整理就越容易照那個窄範圍把影片搬走，錯誤會自我強化
（[design.md 5.2](design.md#52-依收藏夾內容生成描述)）。取樣也刻意涵蓋整個夾子——只讀最新一頁會被
「最近剛丟進去的那一批」帶偏。勾「參考現有描述」（預設開）時，模型會沿用你原本寫的範圍，不會把它改窄。

想把描述寫回 B 站就按「把描述同步回 B 站」。**沒填描述的夾子會被跳過**：送空描述會把 B 站原本的簡介清成空白，
而且不可復原。

## 關注清理最重要的概念：三態，不是兩態

每個帳號查完只會是三種之一：

| 狀態 | 意思 | 畫面上 | 能不能勾選 |
|---|---|---|---|
| 有影片 | B 站回了 `code 0` 且有影片清單 | 顯示最後一支影片的標題、日期、安靜天數 | 可以 |
| 確認無影片 | B 站回了 `code 0` 但清單是空的 | 「沒有影片」、天數欄顯示「從未投稿」並排在最不活躍的那端 | 可以（它比任何門檻都不活躍） |
| 未知 | 請求失敗、B 站回非 0 code、或風控 | 「查不到」＋原因，整列變淡、勾選框鎖著 | **不行**，也不會進匯出 |

還有一種「還沒查」——這一輪被你停掉或被風控停下時剩下的帳號。它們跟「未知」一樣鎖著，左邊分面裡都算在「查不到」，
橫幅上有「補查剩下的 N 個」。

為什麼要這樣：B 站限流時回的是 **HTTP 200 加一個非 0 的 code**，payload 裡沒有影片清單。讀得太天真，
一個天天更新的帳號會被當成「從來沒發過片」而被取關。Java 版就修過這個 bug；這裡把它做成結構：
`canSelect()` 是唯一決定「這列能不能被動手」的地方。

## 一次整理，實際發生的事

### 步驟 1：選來源與範圍

選一個收藏夾當來源。大夾子可以只處理「最近收藏的 N 支」——
B 站的列表本來就依收藏時間新到舊，抓滿 N 支就停，適合分批整理。

### 步驟 2：選目標

勾選「允許 AI 搬進去」的收藏夾。沒勾的夾子，AI 根本不會看到，也就不可能搬進去。
描述與 B 站簡介都空的目標會出現提醒。

### 步驟 3：取資料（這一步決定 AI 看得到什麼）

```
resource/list（每頁最多 40 支，實測有時只回 25 支，會多翻幾頁）
  → 標題、簡介、封面網址、時長、分P 數、UP、收藏時間、是否已失效
  已失效的挑出來，不送去分類

（設定：抓影片詳情）每支 1 次 wbi/view/detail
  → 標籤、合集名稱＋同合集其他影片標題、分區、動態、分P 標題、合作者
  結果存進 IndexedDB 快取 30 天，第二次整理同一批影片不會重打

（設定：抓字幕）掛在詳情後面，每支最多 2 次請求
  → 字幕全文（截 400 字）。人工字幕優先，沒有才用 AI 字幕

（設定：附上封面，需先通過視覺測試）從圖片 CDN 抓 320×200 縮圖轉 base64
  → 快取 7 天
```

三個資料來源各是一個**開關**，沒有中間狀態：抓就每支都抓，不抓就一支都不抓。
以前有過「智慧」那一階（只補文字線索不足的影片），實測分不出差別卻讓估算與流程說明各多三條分支，已經移除。

字幕是**掛在詳情後面**的：詳情關掉時字幕也不會抓。封面則要先通過「測試視覺」才會生效。

### 步驟 4：問 AI

（整理流程與影片頁的「智慧收藏」走的是同一支 `core/classify.ts` 的 `classify()`：
短號、prompt 組裝、退避重試、解析、換回 media_id 全部共用，差別只有「有沒有來源收藏夾」。）

每一批送出去的內容長這樣（實際格式看設定頁的「會送給 AI 什麼」）：

```
【目前所在收藏夾】   ← 少了這塊，模型會傾向把整個夾子搬空
- 名稱：默认收藏夹 | 描述：…

【目標收藏夾】       ← 只有你勾選的；id 是 1..N 的短號，不是 B 站的 media_id
- id=1 名稱：Windows | 描述：…
- id=2 名稱：Music   | 描述：…

【待分類影片】
### 影片 1（BV1…）
標題：… / 標籤：… / 合集：《…》(共 N 集) — 同合集：… / 簡介：… / 分區：… / 時長：… / UP：… / 字幕：…
（視覺模式時，每支影片的封面圖就插在它自己的欄位前面）
```

系統提示後面還會接上你在設定頁寫的「自訂分類指示」（如果有填）。

模型只回一個 JSON：每支影片要進哪些收藏夾（可以是空陣列＝留在原地）、理由 20 字內、
它實際用了哪些欄位（`basis`）、有沒有把握（`confidence`）。回來的短號會立刻換回真正的 `media_id`
——送 10 位數的 media_id 時，較弱的模型會把理由寫對、id 卻抄成別的夾
（[實測](research/classify-eval-2026-08.md#5-收藏夾-id-太長會讓弱模型抄錯已修)）。

批次怎麼分：**有封面的走視覺批次（預設 10 支/批）、沒封面的走文字批次（預設 30 支/批）**，兩種分開送。

### 步驟 5：審核（這一步不會動到任何東西）

一支影片一列：封面、標題、AI 建議的目標、理由、它用了什麼判斷（`標籤 → 合集`）、可以改的目標選擇。

- **低信心的建議不會被預先勾選**——模型自己說在猜的東西，不該因為你直接按「執行搬移」就生效。
- 左軌的分面：全部 / 將搬移 / 將複製 / 不搬 / 低信心 / 已失效 / 已完成 / 失敗，另有一組「只看要搬進某個收藏夾」。
- 每列的「送了什麼」可以看到這支影片所在那一批的完整 system／user 內容與模型的原始回覆。
- 一支影片可以同時進多個收藏夾，這是刻意的（例如同時屬於「音聲」與「百合」）。
- **「也留在原位」＝複製而不是搬移。** 選了目標之後，那一列底下會出現這顆開關與一句「會不會離開來源夾」：
  「搬離來源」按下去就變成「留在來源，另外複製一份出去」，這一列的目標全部改用 `copy`，來源那份完全不動。
  整批要這樣做的話，底部作業列有「全部保留原位」／「全部改為搬走」。
- **AI 自己也會建議這個組合**：它拿到的是「這支最後應該在哪些收藏夾裡」，所以「留在現在的夾子，
  同時也屬於另一個夾」（例如既是「音声」也是「百合」）會直接建議成「保持原位 ＋ 那個夾」，
  預設就是複製。低信心的一樣不預先勾選。

### 步驟 6：執行搬移／複製

- 同一個目標的影片合併成批（每批最多 20 筆），遇到 `-632`（數量限制）自動對半拆。
- 多目標時：前 n-1 個用 `copy`、最後一個用 `move`（copy 全部排在 move 前面，免得來源先被搬走）。
- 勾了「也留在原位」的列**整列都用 `copy`**，一次 `move` 都不發，所以來源那份不會被動到；
  按鈕本身會跟著換字：全是搬移就是「執行搬移」、全是複製就是「執行複製」，混在一起會把兩個數字都寫出來。
- 全部寫入走同一條序列佇列，兩次之間至少間隔設定的毫秒數。
- 中途按「取消」：正在送出的那一批會標成**失敗**（那一批到底寫進去沒有是不確定的），
  可以用「失敗的重新排入」再試一次；還沒開始的維持「待搬移」。
- **撤銷這次搬移**：把搬走的影片放回來源夾，多目標的複本也一併移除；撤銷後那幾列回到「不搬」，
  不會因為再按一次「執行搬移」又重做同樣的決定。保留原位的那幾列**只會移除複製出去的那幾份**，
  來源本來就沒被動過。
- 失效影片：不會被分類，要清掉就在審核表按「移除失效影片」（二次確認，不可復原）。

分類結果與搬移進度會存成快照，關掉分頁再打開可以續跑或重試失敗的。

## 一次清理，實際發生的事

### 準備畫面

打開分頁就會做兩件唯讀的事：問 B 站你關注了幾個人（`relation/stat`，1 個請求），數快取裡有幾個帳號的結果。
然後寫給你看：

- 三個步驟各會花多少（讀清單約每 50 人 1 個請求；查活躍度每人 1 個請求；審核不花請求）
- 作業列右邊的 `≈ N 個請求 / ≈ M 分鐘`
- 要查哪些：**只查沒有新鮮結果的**（建議）或**每個都重查**
- 要不要包含悄悄關注

按「讀取清單並查 N 個帳號」開始。在審核頁確認之前，這個擴充功能不會送出任何會改變帳號的請求。

### 讀清單

```
relation/stat            → 關注數、悄悄關注數（知道要翻幾頁）
relation/tags            → 分組清單（-10 特別關注、0 默认分组、其餘自訂）
relation/followings ×⌈N/50⌉ → 每個帳號：名稱、頭像、分組 id、特別關注、互相關注、關注時間
relation/whispers ×⌈M/50⌉   →（勾了「包含悄悄關注」才會）悄悄關注
```

幾千個關注也只是幾十頁，每次跑都重讀，不快取。

### 查活躍度

每個帳號一次 `space/wbi/arc/search`（空間頁的投稿列表），取最新一支影片；B 站回報投稿總數是 0 才算「沒有影片」，回應對不起來一律當「查不到」。走與整理收藏共用的節流器（依設定頁的讀取速率，預設每秒 2 個、±30% 抖動；關注幾千個的話建議選「保守」的 1 req/s），
有快取且還新鮮（30 天內、而且不是「未知」）的直接沿用。畫面上是儀表：目前階段、`done / total`、已用與預估剩餘、
實際速率、快取命中、查不到的數量，加上最近幾筆請求（端點、參數、狀態碼與耗時）。

遇到 `-352`／`-412`／`-799` 或 HTTP 412：等 60 秒重試、再 120、再 240，還是不行就**整輪停下**，
把已經查到的帶進審核表，剩下的標成「還沒查」。按「停止」也是一樣的結果。

分頁切到背景時 Chrome 會把計時器鉗到每秒一次，速率大約減半；任務期間握著 Web Lock，所以不會整個凍住，
但保持前景會快一倍。

### 審核表

左軌由上而下：

| 區塊 | 說明 |
|---|---|
| 安靜超過 N 天 | 門檻。數字欄位加 180／365／730 三顆常用值；改了整張表立刻重篩，**不重新抓**。這個數字會存起來。 |
| 狀態 | 全部／安靜超過門檻／還在投稿／完全沒有影片／查不到／已取關／已重新關注／失敗，每項帶計數 |
| 關注類型 | 特別關注／互相關注／悄悄關注（有才顯示） |
| 分組 | 不限／沒有分組／你的每個分組，依計數排序 |
| 這一輪 | 帳號數（對照 B 站回報的關注數）、這次查的、用快取、查不到、清單讀於幾點、快照存於幾點 |

三組分面的計數採一般分面搜尋的慣例：每一組的數字反映**其他分面已套用之後**還剩多少。

中央是表格：勾選、帳號（頭像、名稱、mid、認證、互粉／悄悄標記）、分組、最新投稿（標題＋日期，可點開）、
安靜天數（超過門檻的用琥珀色）、關注於、狀態。表頭可以排序（帳號、分組、天數、關注於）；天數排序時
「沒有影片」在最不活躍的那端、「查不到」永遠在最後。一頁 100 列。點列的空白處也能勾選。

上方工具列：搜尋（名稱或整個 UID）、「勾選顯示中的 N 個」（只勾能勾的）、「清除 N 個勾選」。

### 取關

作業列：**取關 N 個帳號** → 按下去變成一句話＋「確定取關 N 個」＋取消。確認後每個帳號一次 `relation/modify`
（一般與互粉用 act 2、悄悄關注用 act 4），依設定頁的「寫入間隔」（預設 800 ms）排開；每一列即時變成「取關中… → 已取關／失敗＋原因」。
可以中途停止，還沒輪到的保持原樣。取關過程中不能改勾選。

取關完成後勾選會清掉（那些列已經不是「可勾選」的了）；左軌多出「已取關」分面。

### 撤銷

只要這次有「已取關」的列，作業列就有 **撤銷——重新關注 N 個**。確認後：

1. 每 20 個一批 `relation/batch/modify`（act 1）重新關注；B 站回報失敗的 mid 標成「無法重新關注」。
2. 依原本的分組（含特別關注 -10）把人放回去：同一組分組簽名的帳號併成一次 `relation/tags/addUsers`。
   分組還原失敗**不算撤銷失敗**（關注關係已經回來了），列上留備註。

做不到的兩件事會直接寫在確認句裡：悄悄關注會變成一般關注（act 3 已下線）；關注日期會是今天。

### 匯出（備用出口）

作業列的「複製 N 個 UID」把勾選列的 UID 以逗號分隔複製到剪貼簿（關注管理器腳本「從 UID 清單匯入」吃的就是這個格式；
沒有剪貼簿權限時改成下載 `.txt`）；「下載 CSV」給名稱、分組、安靜天數、最新投稿、影片連結、個人空間。
兩者都再排除一次「未知」——不管畫面上勾了什麼，未能確認的帳號不會出現在檔案裡。

### 結果快照

跑完會把整張表（含勾選）存進 `chrome.storage.local`，關掉分頁再開會直接回到審核；「清除結果」才會丟掉。
「再查一次」回到準備畫面（上次的結果還在，可以按「回到審核表」）。

## 影片頁的「✨ 智慧收藏」

按下去大約 1.2 秒之後就收好了。中間發生的事：

```
content script（只畫按鈕與卡片，不發請求）
   │  chrome.runtime.sendMessage
   ▼
service worker
   ├─ wbi/view/detail          → 這支影片的標題、標籤、合集、分區…（順手寫進詳情快取）
   ├─ folder/created/list-all  → 你所有的收藏夾 ＋ 這支影片已經在哪些夾裡（fav_state）
   ├─（依設定）封面縮圖         → base64，與文字欄位一起送
   ├─ chat/completions         → 問模型該收進哪個夾（最多 2 個）
   └─ folder/created/list      → 補收藏夾封面（與上面那次 AI 往返平行跑，不多花時間）
   ▼
右下角每個收藏夾一張卡：封面縮圖、「已收藏到《X》」、理由與依據
   ├─ 10 秒後自動消失（滑鼠停在上面會暫停）
   ├─ 卡片下緣有倒數條，看得出「取消收藏」還剩多久
   ├─「取消收藏」把它移出去
   └─「重新選擇」打開帶搜尋的收藏夾清單（AI 建議與已收藏的排在最前面，✨ 標出建議）
```

### 送給 AI 的到底是什麼

和整理流程送的是**同一種格式**（同一組 `formatVideo`／`formatFolders`），差別只在題目：
整理流程問「要不要從現在的夾子搬走」，影片頁問「這支還沒收藏，該收進哪個夾」。

| 欄位 | 影片頁會不會送 | 從哪來 |
|---|---|---|
| 標題、簡介、時長、分P 數、UP | ✅ | `view/detail` 的 `View` |
| 標籤、合集名稱＋同合集其他標題、分區、動態、分P 標題、合作者 | ✅ | 同一個請求的 `Tags` / `ugc_season` / `tid` |
| 封面圖 | **依「附上封面」設定** | 圖片 CDN，快取 7 天 |
| 字幕 | **依「抓字幕」設定**（預設關） | `player/v2` ＋ 字幕 JSON，開了每支多等 1–2 秒 |
| 你所有收藏夾的名稱與描述 | ✅（不只勾選的） | `list-all` ＋ 本機描述／B 站簡介 |
| 自訂分類指示 | ✅ | 設定頁那一欄（接在系統提示後面） |

### 設定在影片頁生效嗎

**每一項都跟。** 影片頁沒有自己的規則。

| 設定 | 影片頁 | 為什麼 |
|---|---|---|
| Base URL／Key／Model／額外請求參數 | ✅ 同一套 | 同一個 `ai/client.ts` |
| 附上封面 | ✅ | 和整理流程同一支 `attachesCover` |
| 抓字幕 | ✅ | 開了每支多等 1–2 秒（多 2 個請求）。要不要付這個代價由你決定，不由程式決定 |
| 讀取與寫入速度 | ✅ | service worker 有自己一份限速器，會跟著設定變更 |
| 自訂分類指示 | ✅ | 影片頁有自己一份系統提示（題目不同），但自訂指示接在兩者後面 |
| 收藏夾描述 | ✅ | 同一支 `effectiveDescription`：本機描述優先，空的時候用 B 站簡介 |
| 抓影片詳情 | 開關在這裡沒有效果 | 影片頁本來就只發一次 `view/detail`，標題與 UP 也是從它來的。關掉不會少打請求，只會讓送出去的欄位變少，所以照樣送 |
| 文字／視覺批次大小 | 不適用 | 一次只有一支影片 |

其他刻意的選擇：

- **低信心或找不到合適的夾就不自動收藏**，直接把挑選器打開讓你選。
- 在「分析中…」時按 ✕ 就是放棄這次收藏：結果回來也不會寫入。
- 寫入走 `resource/deal`（B 站原生收藏彈窗用的同一支 API），成功與否只看 `code`。
- 寫完會把 B 站原生收藏按鈕的狀態切成一致（`.video-fav` 上的 `on` class），數字不動。
- SPA 換片（不重新整理就跳到下一支影片）時，上一支的卡片會全部收掉——留著的話按「取消收藏」動到的是舊影片，
  卻會把新影片的收藏按鈕熄掉。
- 按鈕只 `append` 到工具列**最後面**、而且等 `window load` 之後才掛——插在中間會讓 B 站前端抓到錯的節點，
  整個影片頁停止渲染。

## 設定頁的每一項在做什麼

六章分三組。**01–03 只有整理收藏（連同收藏夾描述、影片頁的智慧收藏）用得到**——它們都要一個 AI 端點；
**04–06 兩個工具共用**；清理關注自己的兩個設定不在設定頁，左軌最後一列是通往關注頁的門。
每一章開頭寫著「用在哪幾個功能、不用在哪個」，每個設定寫著做什麼、預設是什麼；
底部控制列的章節軌標出哪幾章改過沒存（缺口就是「AI 專用／共用」的分界），主按鈕寫著改了幾項。

### 01 AI 端點

| 項目 | 預設 | 說明 |
|---|---|---|
| Base URL / API Key / Model | `https://api.openai.com/v1` ／ 空 ／ `gpt-4o-mini` | 任何 OpenAI 相容端點，Base URL 多數服務要以 `/v1` 結尾。儲存時才對那個網域申請權限；金鑰存在本機、匯出備份時不帶走 |
| 測試連線 | — | 送一句「請只回覆 OK」，看得到端點原樣的回覆 |
| 這個模型看得懂圖片 ＋ 測試視覺 | 關 | 送一張擴充功能自己的圖示，**由你確認模型的描述對得上**（深色圓角方塊、白色勾號、帶圓形播放頭的粉色進度條）才算通過。換模型或 Base URL 要重測 |
| 端點相容性 → Temperature | 留空 | 留空＝不送這個參數（推理模型多半只接受預設值）。**設 0 也不會讓結果穩定**：同一份 prompt 重跑仍有 ~20% 不同 |
| 端點相容性 → 額外請求參數 | 空 | 原樣併進 request body（`model`／`messages`／`stream` 會被忽略）。例如 DeepSeek v4 填 `{"thinking":{"type":"disabled"}}` 關掉思考模式 |

### 02 給 AI 看什麼

| 項目 | 預設 | 實測 |
|---|---|---|
| 抓影片詳情 | 開 | 關掉：命中率 −2pp、低信心變多。標籤是準確度最大的來源 |
| 抓字幕 | 關 | 實測 62 支裡 43 支有字幕、全部是 AI 字幕；全開多 54% token，命中率沒有跑出浮動範圍 |
| 附上封面 | 開（要先通過視覺測試） | 實測沒有穩定方向：有一組是附圖比較好、換成好描述之後反過來。想省 token 就關掉 |
| 批次大小（文字 30 / 視覺 10） | — | 附圖是全有全無，一次只有一個數值生效。視覺批次越大越容易張冠李戴 |

這一章右邊有一條**成本讀數**：以 100 支影片為基準，即時算出這份設定要打幾次 B 站讀取、幾張封面、
幾次 AI 呼叫、大約幾分鐘。改任何一個選項數字就跟著跳，可以直接比較。展開的「會打出哪些請求」是逐項明細，
「會送給 AI 什麼」是用兩支假影片組出來的真實 prompt。

### 03 分類指示

只有一個「自訂分類指示」：接在系統提示後面、優先於內建的判斷原則（輸出格式除外），上限 1000 字。
用來寫只有你知道的分類習慣，例如「MMD 與 3D 舞蹈一律進『繪畫 / 美圖』」。
要改某個收藏夾收什麼，寫它的描述比寫在這裡有效得多。

### 04 讀寫速度

| 項目 | 預設 | 說明 |
|---|---|---|
| 速度 | 預設（2 req/s、800 ms） | 三選一：保守（1 req/s、1500 ms）／預設／快（3 req/s、500 ms）；「自己填數值」可以逐項調（讀取速率、寫入間隔、每次搬移筆數）。讀取抖動固定 ±30%。**整理收藏與清理關注共用**（一次只跑一個）；查關注是每個帳號一個請求，關注幾千個的話選「保守」比較安全 |

### 05 快取與備份

| 項目 | 預設 | 說明 |
|---|---|---|
| 影片快取 | — | 影片詳情 30 天＋封面 7 天，整理收藏重用它們。清掉只會讓下次重抓 |
| 帳號活躍度快取 | — | 每個帳號的最新投稿 30 天（查不到的永遠重查）；清理關注只向 B 站問這裡沒有的帳號。與影片快取在同一個 IndexedDB，各自清 |
| 備份 | — | 把**描述與設定**匯出成 JSON 再匯回來（不含 API Key）——描述是這裡最難重建的東西。設定裡含關注的門檻與「包含悄悄關注」 |

### 06 語言

介面、影片頁按鈕與進度文字的語言（英文預設、繁體中文），改了立刻生效。送給 AI 的內容一律維持中文——那是功能性的輸入，不是介面。

### 清理關注的設定在關注頁上

**安靜超過 N 天**（預設 365）在關注頁左軌改，也可以直接拖審核表時間軸上的播放頭；**包含悄悄關注**（預設開）在關注頁的準備畫面改。
兩個都會存起來，下次打開還是同一個值；設定頁左軌最後一列會顯示目前的門檻並帶你過去。

## 東西存在哪裡

| 存什麼 | 存在哪 | 清掉的方法 |
|---|---|---|
| AI 端點、金鑰、限速、關注門檻等各種設定 | `chrome.storage.local` | 設定頁清空欄位／移除擴充功能 |
| 收藏夾描述、上次勾的目標、整理範圍 | `chrome.storage.local` | 同上 |
| 上一次的分類結果與搬移進度 | `chrome.storage.local`（`lastJob`） | 整理頁審核表的「清除結果」 |
| 上一次的關注審核（表格＋勾選） | `chrome.storage.local`（`lastFollowJob`） | 關注頁的「清除結果」 |
| 影片詳情（30 天）、封面 base64（7 天）、每個帳號的活躍度（30 天） | IndexedDB `bilitidy` | 設定頁「快取」的兩個「清除」，或自動過期 |
| 每批送出的 prompt 與模型回覆、最近幾筆請求 | 只在記憶體 | 重新整理分頁就沒了 |

WBI 簽名金鑰每天更新一次，也放在 `chrome.storage.local`。沒有任何東西離開這個瀏覽器；
B 站那邊只連 `api.bilibili.com`（封面與字幕另外走 `hdslb.com`），AI 那邊只連你自己填的那個端點。

## 出錯的時候

所有錯誤會被歸成幾類，UI 只依類別處理：

| 類別 | 什麼情況 | 行為 |
|---|---|---|
| `auth` | 未登入、找不到 `bili_jct` | 停下來，提示去登入 |
| `riskControl` | `-352`／`-412`／`-799`／HTTP 412／`v_voucher` | 自動等 60→120→240 秒重試，仍失敗就停下並保留進度 |
| `network` | 連不上、5xx | 等 1→2→4 秒重試 |
| `limit` | `-632`（一次搬太多） | 批次自動對半拆，拆到單筆為止 |
| `api` / `parse` | 端點回了看不懂的東西 | 直接顯示訊息，不重試 |
| 逾時 | AI 端點 120 秒沒有回應 | 當成網路錯誤退避重試，不會讓整個任務停在那裡 |

另外：抓不到詳情的影片照樣會送去分類（線索少一點），但統計列會告訴你有幾支；查活躍度時遇到風控或未登入**不會丟例外**——已查到的帳號照樣進審核表、剩下的標成「還沒查」，橫幅上一鍵補查；取關與撤銷遇到致命錯誤也是停下、還沒輪到的保持原樣；
模型只回了思考內容、沒有正式回覆時會直接停下並說明原因（再跑下去整批都解析不出來）。

任務期間分頁會持有一個 Web Lock，避免被 Chrome 凍結；切到背景時 Chrome 仍會鉗制計時器，讀取會變慢，
所以介面會提醒你把分頁留在前景。
